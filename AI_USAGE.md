## 4. What mistakes, insecure suggestions or incorrect assumptions did AI make?

1. **Missed the SSL tunnel attribute.** Claude's first `parser.py` ignored `tunnel="ssl"`. Nmap can report HTTPS as service `http` with a tunnel attribute, so every HTTPS port would have been flagged as "plain HTTP", which is a false positive. Claude found this while reviewing its own parser, before it caused a bad result. I added the `tunnel` field and a `service_key()` function.
2. **Case-sensitive service matching.** The rule listed `x11` but Nmap reports `X11`, so the X11 rule never fired. My hand-made samples never contained it. It was caught when I ran the tool on the real Metasploitable scan and compared the output with the XML. Fixed by lowercasing the service name.
3. **Wrong "Service" column.** For services with a version but no product (rpcbind on 111, nfs on 2049), the report showed only `2` and `2-4`. Found by reading the report. Fixed in `_detected()`.
4. **Silently dropped services.** OpenSSH (22) and BIND (53) have a version but no rule and no CVE entry, so they appeared nowhere in the report. That hides the "no match does not mean safe" limitation. Fixed by adding an "Open services with no rule or CVE match" section.
5. **Wrong CVE data, written from memory.** Claude wrote the CVE scores, version ranges and summaries from memory and said they must be checked. When checked, vsftpd (CVE-2011-2523) and Apache (CVE-2017-7679) were correct. **ProFTPD (CVE-2010-4221) was wrong.** The range started at 1.3.0, but the vulnerable versions start at 1.3.2 (fixed in 1.3.3c). So ProFTPD 1.3.1 on my lab VM was wrongly matched, which was a false positive in my real report. The 9.8 score was also not NVD's: NVD publishes CVSS v2 10.0 for this CVE. A test Claude had written encoded the wrong expectation, so it hid the problem until the check.
6. **Wrong lab-network assumption.** Claude first said Kali needed a second network adapter. My `ip a` output showed both VMs were already on the same subnet, so that step was unnecessary.
7. **Circular test.** `test_report_matches_expected_file` compares the report to a file generated by the same code, so it catches regressions but does not prove the report is correct. Manual checking was needed for that.
8. **Filename risk.** `parser.py` clashes with Python's removed `parser` module on versions older than 3.10, so the project needs Python 3.10+.
9. **Version matching is weaker than it looks.** Ubuntu lists its hardy release as not affected by CVE-2011-2523, because the backdoor was only in one download window. So a version match alone is not proof. This is in the README limitations.

Claude chose `defusedxml` over the standard `xml.etree` to avoid unsafe XML parsing. I did not find any insecure code suggestions.

## 7. Which part of the final project can I confidently explain without AI assistance?

- **The flow:** `parser.py` reads the XML, `analyzer.py` filters, applies rules and matches CVEs, `report.py` writes Markdown, and `nmap_triage.py` connects them.
- **Why `defusedxml`** is used instead of `xml.etree`: it rejects malicious XML such as entity expansion.
- **The three port statuses** (open, unverified, ignored), and why `tcpwrapped` and filtered ports are not findings.
- **Why rules match on service name, not port number,** and why HTTPS needs the `tunnel` check.
- **Why a CVE match is only "potential":** distributions backport fixes, and a version string alone proves nothing.
- **Why non-numeric versions are skipped** (`4.7p1`, `3.X - 4.X`) instead of guessed.
- **What the exit codes mean:** 0 is OK, 1 is a finding at or above `--fail-on`, and 2 is bad input.
- **The real-scan results,** including the ProFTPD false positive and how I found it.
